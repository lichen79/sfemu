# Design: Motorola 68000 Core (sfemu sub-project A)

Date: 2026-08-05
Status: Approved
Scope: Sub-project A of the sfemu arcade emulator

## Context

`sfemu` is an arcade hardware emulator targeting Street Fighter (1987, Capcom's
pre-CPS board) and Street Fighter II (CPS-1). Both boards run a Motorola 68000
main CPU and a Z80 sound CPU driving a YM2151, so the project is one pair of CPU
cores plus two board-specific drivers rather than two emulators.

Decisions already made:

- **Emulate the real hardware**, not a reimplementation of the games.
- **Rust**, native window (winit/pixels or SDL2 for video, cpal for audio).
- **Accuracy target: cycle-counted CPUs with scanline video.** Instruction cycle
  counts are correct and video renders per scanline. Not cycle-exact bus timing.
- **SF2/CPS-1 is the first board to boot**; SF1 follows as a second driver.
- Goals: playable with save states, a debugger, deeply documented hardware
  knowledge, and a core suitable for WASM and rollback netplay.

### ROMs

No ROMs are bundled, fetched, or committed. SF1 and SF2 are commercial Capcom
code. The loader (sub-project B) accepts a **path to a MAME-format ROM set** at
runtime (`sf.zip`, `sfii.zip`), supplied by the user. Legal sources include
Capcom Arcade Stadium, Capcom Fighting Collection, or dumping boards you own.

Every milestone in sub-project A is **ROM-free** and verified against public test
suites.

## Project decomposition

Six sub-projects, each with its own spec, plan, and implementation cycle.

| # | Sub-project | Rationale for position |
|---|-------------|------------------------|
| A | Workspace + M68000 core | Everything depends on it; fully verifiable with zero ROMs |
| B | Bus/timing framework, MAME ROM-set loader, minimal window | First execution of real board code |
| C | CPS-1 video: tilemaps, sprites, palettes, CPS-A/B registers, scanline renderer | Largest piece; where SF2 becomes visible |
| D | Z80 + audio: YM2151, OKI MSM6295 ADPCM | Deferrable — CPS-1 sound is a fire-and-forget latch, so a stubbed Z80 does not block C |
| E | Frontend, debugger, save states | Step/breakpoints/VRAM and tile viewers; the main advantage of a custom emulator over MAME |
| F | SF1 driver: its own board with dual YM2151, MSM5205 voice, second sound Z80 | Second driver against a proven core; validates the abstraction |

**WASM and netplay are not stages.** They are constraints on A–D: the core takes
no threads, no wall-clock access, and no host I/O; it exposes a frame-stepped API
and serializes completely. Honouring this from the start makes both nearly free
later.

**This document specifies sub-project A only.**

### Core public interface

```rust
pub trait Bus {
    fn read8(&mut self, addr: u32) -> u8;
    fn read16(&mut self, addr: u32) -> u16;
    fn write8(&mut self, addr: u32, val: u8);
    fn write16(&mut self, addr: u32, val: u16);
}

pub struct M68k { /* d[8], a[8], pc, sr, usp, ssp, state */ }

impl M68k {
    pub fn reset(&mut self, bus: &mut impl Bus);
    pub fn step(&mut self, bus: &mut impl Bus) -> u32;  // returns cycles consumed
    pub fn set_irq(&mut self, level: u8);               // 0 = none, 1-7 IPL
}
```

Rationale:

- **Everything goes through `Bus`**, so the caller owns all memory, timing, and
  peripherals. The core is a pure function of its state plus bus responses.
- **32-bit accesses are composed from 16-bit accesses**, matching the real chip's
  16-bit data bus. This also yields correct cycle counts without special cases.
- **`step()` returns cycles** rather than the core owning a clock, so sub-project
  B can interleave 68000, Z80, and video deterministically.
- **No interior mutability, no globals, no clock access.** All CPU state is plain
  data, so the struct derives `Clone` and `PartialEq` and can be snapshotted
  wholesale — save states and rollback netplay handled before they are requested.
  To keep the crate dependency-free, `serde` derives are behind an optional
  `serde` feature, off by default; `Clone` alone is enough for netplay rollback.

## Core internals

### Decode

A 64K-entry jump table: `[fn ptr; 65536]` built once at startup, mapping every
opcode word directly to a handler. Illegal entries point at the illegal-
instruction exception handler, so opcode legality stops being scattered logic.
Cost is 512KB of pointers, which is irrelevant at this scale.

Handlers are written by grouping over addressing modes rather than enumerating
65536 cases: `MOVE.W <ea>,<ea>` is one function parameterized by source and
destination mode. Effective-address calculation is a shared helper returning
either a resolved address or a register reference.

### Correctness priorities

Ordered by cost of getting them wrong:

1. **Flags (X N Z V C).** The X flag is not a copy of C; `ADDX`, `SUBX`, and
   `ROXL`/`ROXR` depend on it. V on signed overflow for `ADD`/`SUB`/`MULS`/`DIVS`
   has real edge cases. Wrong flags produce games that run but behave subtly and
   untraceably wrong.
2. **Effective addressing.** Every mode the 68000 encodes: `Dn`, `An`, `(An)`,
   `(An)+`, `-(An)`, `(d16,An)`, `(d8,An,Xn)`, `(xxx).W`, `(xxx).L`, `(d16,PC)`,
   `(d8,PC,Xn)`, and immediate — with mode-specific extension-word decoding.
3. **Exceptions.** Reset, bus error, address error, illegal instruction, divide
   by zero, privilege violation, TRAP, and the 7-level autovectored interrupt
   path with correct stack frames.
4. **Supervisor/user split.** Two stack pointers; SR write restrictions.
5. **Cycle counts.** Per instruction and per addressing mode, taken from the
   68000 User's Manual timing tables.

### Address handling

The 68000 has a 24-bit address bus, so all bus addresses are masked with
`& 0x00FF_FFFF`. Word and long accesses to an odd address raise an **address
error** rather than being silently fixed up: correct board code will not do this,
so surfacing it is more useful than mystery corruption.

"Raise an address error" means taking the emulated exception (vector 3), not
panicking — see the never-panic invariant under Error handling. The frontend may
optionally surface it to the developer as a debugger break, which is where
"loudness" belongs.

### Out of scope for A

- No instruction prefetch queue modelling.
- No bus-arbitration or DMA contention.
- No 68010+ instructions.

The chosen accuracy target means the core is correct **per instruction** and the
sum of cycles is right, without modelling sub-instruction bus ordering.

## Verification

Without ROMs, the test suites are the definition of done.

### Primary: TomHarte/ProcessorTests 68000 vectors

A public JSON suite with thousands of cases per opcode. Each case gives initial
registers and memory, final registers and memory, and the expected bus
transaction list with cycle counts. `testrunner` fetches these into `testdata/`
(gitignored). Each opcode group becomes its own `#[test]`, so a failure names the
instruction rather than reporting "68000 broken".

This allows the core to be proven correct opcode by opcode before any CPS-1 code
exists. Nearly every hard bug in a 68000 core is caught here.

**Known unknown:** the exact repo layout and JSON field names are not known in
advance. `testrunner` will be written against the actual fetched files. If the
suite proves unusable, the fallback is Tiny68k plus hand-written vectors — slower
to full confidence, but not blocking.

### Secondary: Tiny68k / 68ktest

A self-checking 68000 assembly diagnostic, run against a flat-memory `Bus` impl.
Catches integration-level problems the per-opcode vectors cannot: exception
nesting, interrupt timing, and realistic instruction sequences.

### Ours

- Unit tests per flag rule with hand-computed expectations, concentrating on X
  and V edge cases.
- A logging `Bus` impl so tests can assert **access order**, not only end state.

### Definition of done for sub-project A

- 100% of ProcessorTests opcode groups pass, for every opcode the 68000 (not
  68010+) implements. Register/memory final state and cycle counts must match;
  the per-access bus transaction *order* within an instruction is checked only
  where the suite's ordering reflects real 68000 behavior our model covers —
  since prefetch modelling is out of scope, ordering mismatches attributable to
  prefetch are recorded as known deviations in `docs/hardware/` rather than
  treated as failures.
- Tiny68k reports success.
- `cargo clippy` clean with no warnings; `cargo fmt --check` clean.
- A benchmark showing the core sustains **≥10 MHz simulated** on the development
  machine — CPS-1's actual 68000 clock — confirming performance is adequate
  before building on top. Measured in release mode on a mixed instruction
  workload, not a tight `NOP` loop.
- The disassembler round-trips every opcode the decode table accepts without
  panicking.

## Error handling

Two kinds, kept strictly separate.

**Guest faults** — the emulated program misbehaves: address error, illegal
opcode, divide by zero. These are *emulated*, never Rust errors. The core takes
the exception exactly as hardware would, because real ROM code may rely on it.

**Host faults** — our setup is wrong: missing test data, malformed JSON,
unreadable file. These are `Result` with real error types, in `testrunner`.

**Invariant: the core never panics on guest input.** Any byte sequence must be
executable without crashing the emulator, because arbitrary bytes are exactly
what a mis-emulated jump produces. Rust panics are reserved for genuine internal
invariant violations. Invariants too costly to check in release are guarded by
debug-only assertions.

## Implementation order

Test-first throughout: for each opcode group, wire its ProcessorTests case before
the handler, watch it fail, then implement. The suite provides the oracle, so TDD
is natural here in a way it often is not.

Each stage ends with a green test run.

1. Reset, `Bus` trait, register file, jump-table scaffold, illegal-instruction
   exception — so any unimplemented opcode fails loudly and identifiably.
2. `MOVE` across all addressing modes — proves the EA machinery everything else
   reuses.
3. Arithmetic and logic with flags: `ADD`, `SUB`, `CMP`, `AND`, `OR`, `EOR`,
   `NOT`, `NEG`, then `ADDX`, `SUBX`.
4. Shifts and rotates; `BTST`, `BSET`, `BCLR`, `BCHG`.
5. Branches: `Bcc`, `DBcc`, `JMP`, `JSR`, `RTS`, `RTE`, `Scc`.
6. `MULU`, `MULS`, `DIVU`, `DIVS` — divide has the nastiest edge cases
   (overflow, divide by zero).
7. Exceptions and interrupts end to end; then Tiny68k.
8. Cycle-count pass against the timing tables; then the benchmark.

## Two additions included in A

Both are cheap now and pay off in later sub-projects:

- **A standalone disassembler** in `m68k`, sharing the decode table. Required by
  E's debugger and indispensable for reading SF2's code during C.
- **Hardware notes accumulating in `docs/hardware/`** as behavior is confirmed.
  This makes the "learn the hardware deeply" goal concrete rather than
  aspirational.

## Sources to consult during implementation

The broad shape of both boards is known (CPS-1: 68000 at 10 MHz, Z80 at
3.58 MHz, 384×224, three scroll layers, per-game CPS-B chip variants), but exact
register maps, interrupt scanlines, and SF1 specifics must be **verified against
MAME and FBNeo sources during implementation** rather than asserted here.
Naming follows MAME's conventions (`cps1.cpp`, `sf.cpp` register names) so that
diffing our behavior against those sources stays readable.

Primary references: Motorola M68000 Family Programmer's Reference Manual and
User's Manual for CPU behavior and timing tables; MAME/FBNeo sources for board
specifics.
