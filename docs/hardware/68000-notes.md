# 68000 hardware notes

Confirmed behavior, recorded as we verify it. Everything here is backed by a
test in the suite or an explicit measurement — not by recollection.

## Prefetch queue

The 68000 keeps two prefetched words. `prefetch[0]` is the instruction word
currently executing; `prefetch[1]` is the next word already read. `PC` sits 4
bytes beyond the executing instruction word.

Confirmed from `ADD.b` case 000: `pc = 0x32CBB6`, `prefetch = [0xD72A,
0x9CBC]`, and RAM at `0x32CBB2` (= pc-4) holds `D72A`.

## Pipeline / dispatch model

`step_with` peeks at `prefetch[0]` without shifting the queue or issuing any
bus cycle.

`consume_opcode` advances the pipeline by one word: it promotes slot 1 to slot
0, reads the next word from PC into slot 1, and increments PC by 2.  This is
the same bus operation as `fetch_word` — the bodies are identical; the
distinction is intent only.  `consume_opcode` is for the opcode word itself
(value already in hand); `fetch_word` is for extension words where the returned
value is needed.

**Placement within a handler's bus sequence is per-instruction** — the
pipeline-advance read is not always first.  Measured across the suite:
- 199,165 cases: pipeline-advance is the first access.
- 117,105 cases: one or more data reads or writes precede it (e.g. predecrement
  addressing, BSR stack push).

Concrete counterexample: `ABCD -(A3),-(A5)` — two data reads, then the
pipeline-advance, then the result write.  A handler that calls `consume_opcode`
first would emit the pipeline read out of order.

Each handler's bus sequence must be derived from the vector data; do not assume
any fixed ordering.

Exception-aborting handlers (illegal opcode, Line-A, Line-F, TRAP, …) do not
call `consume_opcode` at all.  They return immediately after `exception::take`,
which calls `refill_prefetch_dyn` to overwrite both slots at the vector
handler's PC — matching the hardware pipeline abort.

## Exception frames

Group 1/2 exceptions write a short frame in a non-sequential bus order:

1. `PC[15:0]` → `old_SSP − 2`  (highest address in the frame)
2. `SR`       → `old_SSP − 6`  (lowest address; new SSP lands here)
3. `PC[31:16]` → `old_SSP − 4` (middle of the frame)

The result in memory is a canonical big-endian long PC followed by the SR word,
with new SSP pointing at the SR.  The stacked PC for an illegal instruction
points at the offending opcode, i.e. `cpu.pc − 4` at handler entry.

Vectors confirmed: 4 illegal, 10 Line-A, 11 Line-F.

## Known-bad suite groups

`TAS` and `TRAPV` are documented upstream as not verified: TAS's 5-cycle
read-modify-write timing is not modelled by the generator, and TRAPV behaves
oddly with respect to the S bit. Treated as expected failures.
