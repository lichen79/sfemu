# 68000 hardware notes

Confirmed behavior, recorded as we verify it. Everything here is backed by a
test in the suite or an explicit measurement — not by recollection.

## The timing law

```
cycles = 4 * (number of bus accesses) + (total idle cycles)
```

Verified over all 127 groups and all 317,500 cases: `length == 4*accesses + idle`
holds **317,500/317,500**, every access is exactly 4 cycles, and no group
mismatches. An "access" is any transaction that is not `Idle`.

**The aborted address-error access counts as an access**, even though the CPU
never asserts AS and the core must not emit it. Excluding it drops the law to
**261,894/317,500** — a 55,606-case failure spread across every group that
contains an address error, which looks like a broken timing model and is in fact a
one-line accounting choice. The harness hides the aborted access from the bus
*log* because the core must not perform it; that is a different question from
whether the 68000 pays for it.

Consequence for implementation: if a handler performs the right accesses in the
right order — which the harness already forces, since it compares the sequence in
order — the `4 * accesses` term is correct for free, and **idle is the only
quantity left to model**. So cycle counts belong in code as an access count plus
an idle term, never as memorised totals: a table of totals can drift out of
agreement with the bus sequence, and the decomposition cannot. This also makes
failures unambiguous — a matching sequence with a wrong count is a bug in the idle
term and nowhere else.

Idle *placement* within the sequence is per-instruction (leading, trailing and
middle all occur, and 83,925 cases have two or more). The harness compares only
accesses, so placement never affects pass/fail. Model the total.

## Prefetch queue

The 68000 keeps two prefetched words. `prefetch[0]` is the instruction word
currently executing; `prefetch[1]` is the next word already read. `PC` sits 4
bytes beyond the executing instruction word.

Confirmed from `ADD.b` case 000: `pc = 0x32CBB6`, `prefetch = [0xD72A,
0x9CBC]`, and RAM at `0x32CBB2` (= pc-4) holds `D72A`.

## Pipeline / dispatch model

`step_with` peeks at `prefetch[0]` without shifting the queue or issuing any
bus cycle.

`consume_opcode` advances the pipeline by one word: it promotes slot 1 to slot
0, reads the next word from PC into slot 1, and increments PC by 2.  This is
the same bus operation as `fetch_word` — the bodies are identical; the
distinction is intent only.  `consume_opcode` is for the opcode word itself
(value already in hand); `fetch_word` is for extension words where the returned
value is needed.

**Placement within a handler's bus sequence is per-instruction** — the
pipeline-advance read is not always first.  Measured across the suite:
- 199,165 cases: pipeline-advance is the first access.
- 117,105 cases: one or more data reads or writes precede it (e.g. predecrement
  addressing, BSR stack push).

Concrete counterexample: `ABCD -(A3),-(A5)` — two data reads, then the
pipeline-advance, then the result write.  A handler that calls `consume_opcode`
first would emit the pipeline read out of order.

Each handler's bus sequence must be derived from the vector data; do not assume
any fixed ordering.

Exception-aborting handlers (illegal opcode, Line-A, Line-F, TRAP, …) do not
call `consume_opcode` at all.  They return immediately after `exception::take`,
which calls `refill_prefetch_dyn` to overwrite both slots at the vector
handler's PC — matching the hardware pipeline abort.

## Exception frames

Group 1/2 exceptions write a short frame in a non-sequential bus order:

1. `PC[15:0]` → `old_SSP − 2`  (highest address in the frame)
2. `SR`       → `old_SSP − 6`  (lowest address; new SSP lands here)
3. `PC[31:16]` → `old_SSP − 4` (middle of the frame)

The result in memory is a canonical big-endian long PC followed by the SR word,
with new SSP pointing at the SR.  The stacked PC for an illegal instruction
points at the offending opcode, i.e. `cpu.pc − 4` at handler entry.

Vectors confirmed: 4 illegal, 10 Line-A, 11 Line-F.

## Effective addressing

Program fetches land at `opcode_addr + 4 + 2i` — two words *ahead* of the
instruction word being consumed. So an operand's extension words are frequently
already sitting in the prefetch queue before the bus cycle that refills the queue
behind them. `MOVE.b (An),abs.L` performs its destination write after only **one**
program fetch, yet needs both halves of a 32-bit absolute address.

Consequence: `ea::resolve` is a **pure function taking extension words as
values**, never fetching them. A resolver that called `fetch_word` per extension
word emits program reads at the wrong points in the bus sequence, and the harness
compares that sequence in order. Handlers own the fetch scheduling.

`(An)+` and `-(An)` update the address register during resolution, and the
adjustment is observable when a later access faults. Most buckets keep it; three
do not, and the exceptions are tabled in `ops::move_::roll_back_fault_adjustment`
rather than derived.

## 32-bit write orders

There is no single `write32` helper, because **four distinct orders coexist** and
no shared helper can express all of them:

1. `MOVE.l` / `MOVEM.l` into `-(An)` — descending, **low word first**
2. `LINK` and `PEA` — high word first
3. the exception frame — non-sequential: `PC_lo`, `SR`, `PC_hi`
4. every other `MOVE.l` destination — high word first, ascending

Order 2 is worth stating explicitly because it is the counter-intuitive one:
`LINK` and `PEA` both push to `-(SP)`, and order 1 says a predecrementing long
writes low word first — yet these two write **high word first**, 2,500/2,500 each.
The distinction is that `-(An)` in order 1 is an *addressing mode* being stepped by
the operand size, whereas `LINK`/`PEA` compute `SP - 4` once and then write
forward from it. Reaching for the predecrement helper here is the natural mistake
and it fails only on transaction order, the memory image being identical.

Measured over the MOVE groups: `-(An)` is descending 147/147, and every other
memory destination is ascending (`(An)` 156, `(An)+` 143, `d16(An)` 126,
`(d8,An,Xn)` 126, `abs.W` 16, `abs.L` 17). This is consistent — a predecrementing
destination writes downward from the top of the operand — but the direction is a
property of the addressing mode, not of the address, so it cannot be inferred at
the point of the write.

A predecrementing long therefore *faults on its low word*: the stacked address is
`base + 2`, not `base` (108/108).

`BSR` and `JSR`'s return-address push is order 2 above: **high word first,
ascending**, to `SP` and `SP+2` after `SP -= 4`. 2,570/2,570 two-write cases, all
of which discriminate against low-word-first (the two halves of a return address
never coincide in this corpus), with zero counterexamples. Worth stating alongside
order 3 because the two are easy to conflate and produce
plausible-looking-but-wrong memory either way:

```
BSR / JSR      SP+0 <- PC[31:16]     SP+2 <- PC[15:0]        two writes, ascending
exception      SP+4 <- PC[15:0]  then SP+0 <- SR  then SP+2 <- PC[31:16]
```

Both leave a canonical big-endian longword in memory. The difference is entirely
in the *bus order*, which is what the harness compares — so a subroutine call
written with the exception frame's interleaving fails on transaction order while
its final memory image looks right.

## Branch and jump displacement base

`Bcc`, `BRA`, `BSR` and `DBcc` all compute their target from the address of the
word *after* the opcode:

```
target = opcode_addr + 2 + sign_extend(displacement)
```

With the queue model above (`PC = opcode_addr + 4`) that base is `pc - 2`, and in
the 16-bit displacement form it is the displacement word's own address. Re-derived
per form, with the rival base scoring zero every time:

```
                base = opcode+2      base = opcode      taken, non-faulting
Bcc  8-bit               669                 0                  669
Bcc 16-bit                 5                 0                    5
BSR  8-bit              1223                 0                 1223
BSR 16-bit                 6                 0                    6
                        ----                --                  ----
                        1903                 0                 1903
```

⚠️ **Two things about that table are the finding, not the arithmetic.**

*Check the addition, not just the components.* A previous version totalled these
four counts as **1,898**. All four components were right; `669 + 5 + 1223 + 6 =
1903`. A bare arithmetic slip inside a total reads exactly like a measurement, and
nothing about the number's appearance distinguishes the two. (`674/674` and
`1,229/1,229` above are the same 1,903 grouped by instruction instead of by form.)

*The correct filter for "non-faulting" is the aborted access, not the S-bit gain.*
Filtering on "SR gained S" leaves the denominator at 1,875 `BSR` and 1,021 `Bcc` —
the diluted figures — because **1,006** faulting cases were *already* in supervisor
mode, so there is no S transition to see. Every one of those 1,006 has an odd target
and an aborted access; the census is unanimous. Nor can you filter on `ssp`
changing: `BSR` pushes a return address, so that predicate silently discards 562
legitimate `BSR` cases. This is the same lesson as the vector-fetch predicate below
— identify a fault by its **aborted access**, which nothing else can imitate.

⚠️ **This base has been miswritten in a *comment* three times on this branch, and
the implementation was correct every time** (`branch.rs:262`, and the `opcode_addr +
2` extension-word base at `:438`, `:454`, `:507`, `:541`). The lesson is not "check
the code"; it is that a prose restatement of a measured rule is an independent place
for the rule to go wrong, and it has a worse failure mode than the code, because
nothing executes it. Every figure in this section is now derived by a query, not
restated.

`disp8 == 0x00` selects the 4-byte word form. `disp8 == 0xFF` is an ordinary `-1`
byte displacement on a 68000, **not** a 68020 32-bit form: the 6 non-faulting
not-taken cases with that field all show a `+2` instruction length, and `+6` occurs
**0** times.

A `Bcc` with an 8-bit displacement field of `0x00` takes a 16-bit displacement from
the following word. That word is **already in `prefetch[1]`**, so reading it costs
no bus access — which is why a taken 16-bit branch and a taken 8-bit one have the
same two-access sequence and the same 10 cycles. Only the *not-taken* pair differ
(8 vs 12 cycles), because the wide form must advance the queue twice.

The PC receives the full **unmasked 32-bit** target; only bus addresses are masked
to 24 bits. Scored on the cases where the two differ, the unmasked rule is
1,018/1,018 for `JMP`, 1,116/1,116 for `JSR`, 1,259/1,259 for `RTS` and
1,280/1,280 for `RTR`, and the masked rival scores 0 on every one of those subsets.

`JSR`'s two writes fall **between** the two words of the target refill
(`R target`, `W SP`, `W SP+2`, `R target+2`), which is why it cannot go through the
shared single-`<ea>` schedule. `BSR` pushes before its target-alignment fault;
`JSR` does not. `RTS` and `RTR` commit their stack pop before it, and `RTR`
restores the CCR before it. Each of those is a measured presence or absence, not an
inference — see `ops::branch`.

## Address registers hold 32 bits; only the bus is 24

The 68000 has 24 address pins, so `ADDR_MASK = 0x00FF_FFFF` applies when an address
is **placed on the bus** — and never when a computed address is **stored into**
`An`, `SP` or the PC. An address register keeps all 32 bits.

`LINK` proves it, because `SP := (SP - 4) + d16` can carry out of bit 23:

```
final SP unmasked  2500/2500      masked to 24 bits  2493/2500
7 discriminating cases, all 7 to unmasked
```

With `SP0 = 0x00FFCA8A, d16 = 17494` the result is `0x01000EDC`, not `0x00000EDC`;
with `SP0 = 0x000055FE, d16 = -23418` it is `0xFFFFFA80`, not `0x00FFFA80`.

Only 7 of 2,500 cases discriminate, so a core that masks on store passes almost
everything and fails late. The asymmetry — mask at `read16`/`write16`, never at the
register write — is deliberate and load-bearing, not an inconsistency to tidy up.

## Byte transactions: the strobes place the byte, not the address

The 68000 has a 16-bit data bus and no `A0` pin. A byte access asserts exactly one
data strobe — `UDS` for an even byte address, `LDS` for an odd one — and the datum
travels on the corresponding half of the bus.

**A logged transaction's `addr` is therefore already word-aligned: bit 0 is
cleared, and the byte's address parity is not recoverable from it.** Read the
strobes instead:

```rust
let byte = if t.uds != 0 { (t.data >> 8) as u8 } else { t.data as u8 };
```

From `NBCD (A5)`, where `A5 = 0xDA918AE9` (odd): the transaction is
`Read fc=1 addr=918AE8 data=009E uds=0 lds=1`. The address lost its low bit; only
`lds=1` says the operand is `0x9E` rather than `0x00`.

Deriving the half from `addr & 1` scores 479/1244 on `ABCD -(Ay),-(Ax)`, and
reading `data as u8` unconditionally scores 415/1244. **A score near 50% on a
binary placement choice is this bug's signature**, not evidence of a broken
arithmetic model — half the corpus lands on each parity, so a coin-flip placement
rule looks like a half-right algorithm.

This matters wherever a byte operand is recovered from or compared against the bus
log; it does not affect the CPU itself, whose `Bus` trait takes a full byte address
and does the strobe decode internally.

## Shift and rotate flags

Three rules a reader is likely to get wrong from the manual alone. All three were
scored only on the cases where the rule and its plausible rival predict different
CCRs, over the 55,139 non-faulting register/immediate cases in the 24 sized
groups.

### A zero-length `ROXL`/`ROXR` puts X into C

A shift count of 0 leaves the operand and X alone and clears V — that much is
uncontroversial. C is *not* simply cleared:

```
count == 0:  operand unchanged, X unchanged, V cleared,
             N/Z from the unshifted operand,
             C = 0    for ASL/ASR/LSL/LSR/ROL/ROR   (179/179 discriminating)
             C = X    for ROXL/ROXR                  (61/61 discriminating)
```

This is not a special case bolted onto the rotate: a rotate through X is a
`bits + 1`-wide rotation with X as the extra bit, so a zero-length rotation still
reports the X that sits in the chain. Implemented that way in
`ops::shift::shift`, it needs no separate branch beyond the shared count-0 arm.

Zero counts reach the CPU only through the register-count form — the immediate
form encodes `000` as 8, so there is no zero-length immediate shift.

### `ASL`'s V is a mid-shift predicate, not an endpoint comparison

V is set if the sign bit differed at **any** step of the shift. Comparing the
initial sign to the final sign is a different predicate and fits about 25% of
cases: `0x80` shifted left twice as a byte ends at `0x00`, so both endpoints read
as positive while a sign change plainly occurred. The mid-shift rule is
13,793/13,793 and wins 2,938/2,938 of the cases where the two disagree.

Stated without simulating each step: shifting left by `count` moves `count + 1`
bits through the sign position, so V is set unless those top `count + 1` bits are
all equal. Two details are load-bearing:

- **The `count >= bits` branch.** A byte `0xFF` shifted left by 18 does pass
  through a sign change; V is set for any nonzero operand once everything is
  shifted out.
- **Compute it in `u64`.** At 32 bits `1u32 << 32` panics in a debug build, and
  masking it away instead makes `ASL.l` score 39/1248.

`ASR` never sets V at all (0 in 6,903 cases, 3,477/3,477 against the endpoint
rule): an arithmetic right shift replicates the sign, so the sign cannot change.
Neither does any `LS`, `RO` or `ROX` form (37,941/37,941).

### `ROL`/`ROR` leave X alone

Everything else sets X from C. 6,859/6,859 preserved for the plain rotates;
6,646/6,646 (`ROX`) and 13,610/13,610 (`AS`/`LS`) set from C — the latter
restricted to a nonzero count, since all 118 apparent counterexamples are
count-0 cases where X is preserved instead.

## Bit operations touch only Z

Across all 10,000 `BTST`/`BSET`/`BCLR`/`BCHG` cases the union of SR bits that
ever differ between the initial and final state is `0004` — Z alone. N, V, C and
X are **preserved, not cleared**, so these must not be routed through
`flags::logic_flags`, which clears V and C.

A union of one bit is also what a broken census would report, so the claim needs
its control group: under the same measurement code `AND.b` and `NOT.b` give
`000F`, and `ASL.b` and `ROXL.b` give `001F`. The absence is real.

Z reflects the tested bit as it stood **before** any modification, which is the
whole difference between `BSET` and an `OR`.

The bit number is taken **mod 32** for a data-register destination and **mod 8**
for every other operand, the latter because every non-register operand of these
instructions is a byte. Scored on the discriminating cases only: register
destination 608/608 for mod 32 with mod 8 and mod 16 at 0; byte operand 2,057/2,057
for mod 8 with mod 32 at 0. The byte rule also covers the operands that are not
data-space memory — `d16(PC)` 19/19, `(d8,PC,Xn)` 17/17, and `BTST`'s immediate
operand 20/20.

## BCD: two different models, and V is not undefined

`ABCD` and `SBCD` are not mirror images of each other, and modelling them with one
shared helper does not work.

- **`ABCD` is nibble-wise.** Correct each nibble as you go. The low nibble's carry
  into the high nibble can be **2**, not just 1: `0xF + 0xF + 1 = 0x1F`, `+6 =
  0x25`. Take `lo >> 4`; treating the carry as a bool costs 83 of 1,256 cases.
  A byte-wise `if sum > 0x99 { sum += 0x60 }` model scores 1,240/1,256.
- **`SBCD` is byte-wise.** Subtract in binary, then apply two independent
  corrections — `-6` if the low nibble borrowed, `-0x60` if the byte borrowed —
  both decided from the *uncorrected* subtraction. A nibble-wise model scores
  1,222/1,230, because it propagates the low nibble's `-6` as a borrow into the
  high nibble and the hardware does not.
- **`NBCD` is `0 - Dn - X`**, i.e. `SBCD` with operands in that order. Reversing
  them scores 40/2,097.

`C` is the borrow/carry out after correction, and `X == C`. `Z` accumulates
(`Z_final = (result == 0) && Z_initial`). `N` is bit 7 of the corrected result.

**`V` is documented as undefined, but the hardware is deterministic and
directional.** Compare the MSB of the uncorrected binary result with the MSB of the
corrected one:

| instruction | `V` is set when the MSB goes |
|---|---|
| `ABCD` | `0` → `1` |
| `SBCD`, `NBCD` | `1` → `0` |

The reversal mirrors ordinary add-versus-subtract overflow. A direction-agnostic
"the MSB flipped" rule scores 753/1,256 on `ABCD`. `V` is genuinely set often —
360/1,256 `ABCD`, 299/1,230 `SBCD`, 165/403 `NBCD` — so "`V` is cleared" is not a
harmless simplification.

All six rules are exact over **7,500 cases**, register and memory forms alike
(register: 1256 / 1230 / 403; memory: 1244 / 1270 / 2097).

## CHK

The trap condition is **signed**: `dval < 0 || dval > bound`, where `bound` is
sign-extended from the operation size. An unsigned reading scores 232/376, losing
all 144 discriminating cases.

Own idle cycles, exact at 376/376 across six unanimous buckets:

```
no trap                                                        6
trapping, dval < 0, not (dval > bound), (dval-bound) fits i16  12
otherwise trapping                                             10
```

The discriminating variable in the trapping case is whether `dval - bound`
**overflows i16** — not the sign of `dval`, which scores a misleadingly plausible
225/305 (74%). The standard `+2` EA idle for modes 4 and 6 applies on top,
unchanged.

### One CCR rule covers both paths

`N` and `Z` come from the **tested value**, `V` and `C` are cleared, `X` is kept.
On the trapping path that is what the frame's SR word holds — which means the CCR
must be set *before* the frame is written. 1523/1523 reading the stacked word.

85 trapping cases show a stacked SR equal to the initial one, which looks like
evidence for "CHK leaves the CCR alone when it traps". It is not: those are
exactly the cases where the two readings coincide. Bucketing separates them; a
score does not.

### The stacked PC is past the whole instruction

```
stacked PC = opcode_addr + 2 * (1 + ext_words)     1326 / 1326
rival: fixed opcode_addr + 2                        851 / 1326
```

Per addressing mode, every bucket a singleton: `+2` for modes 0/2/3/4, `+4` for
5/6 and (7,0)/(7,2)/(7,3)/(7,4), `+6` for (7,1) `abs.L`.

The same rule Task 8 measured for `JSR`'s stacked PC and return address
(2570/2570). **64% is the signature of this mistake**, not of a rule needing a
tweak: `cpu.pc - 2` equals the right answer exactly when `ext_words == 0`, so a
fixed offset scores high enough to look like a near-miss while being keyed on the
wrong variable.

### PC-relative CHK

The 94 `(d16,PC)` / `(d8,PC,Xn)` cases resist the usual operand recovery: the
bound is fetched from *program* space, and separating that read from a prefetch
refill means modelling the queue. They are not excluded from the group, though —
`CHK` passes 2500/2500 including all 94, so the standard EA ladder (`7/2` like
`7/0` at `+8`, `7/3` like mode 6 at `+10`) is **confirmed by execution** even
though it was not confirmable by bucketing. Worth keeping in mind as a general
move: an operand you cannot recover offline can still be verified end-to-end.

### A trapping instruction does not advance the prefetch queue

A trapping `CHK Dn,Dn` logs seven accesses — 3 frame writes, 2 vector reads, 2
prefetch refills — and no eighth for a queue advance, because the pipeline
aborted before it. `cycles - idle` buckets at 28 / 32 / 36 / 40 across the
addressing modes, and 28 is `4 * 7` for the register form, which performs no
other access at all.

## Multiply and divide timing

Both are data-dependent, and both are closed-form. Each formula gives the
instruction's *own* idle; the standard `+2` EA idle for modes 4, 6 and (7,3) adds
on top, with **no per-mode multiply or divide correction** — the residual map is
empty, so nothing hides behind the totals.

```
MULU  idle = 34 + 2 * popcount(src)
MULS  idle = 34 + 2 * (count of 01/10 bit-pairs in (src << 1))
```

The base is **34**, not the manual's familiar 38: the published number is a total
including the opcode fetch, which the timing law already charges 4 for. Every case
misses by exactly 4 with the wrong base — and per the timing law's diagnostic
corollary a uniform ±4 means a miscounted *access*, so this looks exactly like a
schedule bug and is not one.

`DIVU` simulates the shift-subtract loop: base 72, `+4` per iteration over 15
iterations, `-2` when the trial subtraction succeeds, and iterations whose MSB was
already set are free. An early first attempt scored 159/323 with every miss
satisfying `want = 2*got - 80` — **a miss set fitting one linear relation is a
scaling bug, not a failed model.**

`DIVS` has two traps worth naming:

- **The base is a function of the sign pair, not of the quotient's sign.** The
  four bases are `(+,+)` 116, `(+,-)` 118, `(-,-)` 120, `(-,+)` 122. A
  negative-quotient rule coincides on three of the four pairs and scores
  1240/1442 — 86%, the wrong variable rather than a near-miss. Solving the base
  per sign pair and requiring each bucket to be unanimous is what settles it.
- **The timing shortcut's predicate is not the `V` flag's, and `DIVS` therefore
  has two distinct overflow paths.** The shortcut — the hardware's pre-division
  test — fires on `|dividend| >> 16 >= |divisor|`; `V` is set on the quotient
  leaving `i16` range. These **disagree on 402 of 1,518 cases**, one-sidedly: the
  shortcut is strictly *weaker*, firing on 760 cases to `V`'s 1,162, with **zero**
  cases where it fires and `V` is clear.

  ```
  early overflow  shortcut fires   fast abort, V set, Dn unchanged    760
  late overflow   shortcut misses  FULL slow cost, V set, Dn unchanged 402
  clean divide    neither          quotient and remainder written      356
                                                                     ----
                                                                     1518
  ```

  The middle row is the one that surprises: the division runs to completion, the
  quotient turns out not to fit, and the instruction pays full price anyway.
  Measured on the register-source subset (99 cases): `V` set 99/99, `Dn` unchanged
  99/99, cycles 126..146 — the slow range, never the fast 16/18. Example
  `0x462A588A / 0x5925`: true quotient 51583, and 130 cycles spent to discover it.

  So `V` set and `Dn` untouched is the outcome for **both** paths; only the cost
  differs. Returning early on the quotient-range test undercounts 402 cases by
  ~120 cycles, which reads as a broken constant rather than a wrong predicate.

  For `DIVU` the two predicates are arithmetically equivalent (0 disagreements out
  of 1,546) — for unsigned division `(dividend >> 16) >= divisor` *is* exactly the
  quotient-overflow condition. That equivalence is what lets "compute one
  predicate, use it twice" pass `DIVU` completely and fail `DIVS` on 402 cases.

The iteration term is two cycles per **zero** bit in the low 15 of
`|quotient| >> 1` — the opposite polarity to `MULU`'s popcount.

Also: the divisor's sign bit is **bit 15**. It is the word operand, so reading it
as `i32` is a silent bug that works whenever the high word is zero.

### Divide overflow

`V` set, destination **completely unchanged**, no exception raised — 791/791 and
1162/1162. And on that path `N` is **set** and `Z` **clear**, unanimously in both
groups; they are not preserved. A full bit census settles this, and reading `Z`'s
bucket as `N`'s is an easy way to conclude the opposite.

`DIVS` overflows far more often than `DIVU` (1,162 vs 791 cases) because the
signed quotient range is half as wide. An unsigned range check on `DIVS` fails
roughly 371 cases, and that count is the diagnostic.

Otherwise `Dn = (remainder << 16) | quotient`, with `N`/`Z` from the quotient's
low word.

### Divide by zero — EXTRAPOLATED, not measured

**The suite contains no divide-by-zero case at all.** 0 of 1,546 `DIVU` and 0 of
1,518 `DIVS`, against a control that recovers 1,525 and 1,502 *distinct* nonzero
divisors with the same code — the query can see a divisor, so the absence is a
property of the data. Write counts in both groups are only 0 (non-faulting) and 7
(address-error frames): there is no 3-write case to compare a group-2 frame
against.

So a green `DIVU`/`DIVS` group says nothing about this path — not the vector, not
the stacked PC, not the cycle count, not whether the destination is preserved.
`ops::muldiv`'s unit tests are its only coverage. What is implemented:

| aspect | value | basis |
|---|---|---|
| vector | 5 | the manual |
| stacked PC | `opcode_addr + 2 * (1 + ext_words)` | `CHK` and `JSR`, both measured |
| cycles | schedule so far + `4 * 7` frame accesses + 10 idle | `CHK`'s trapping rule; the 10 is a **guess** — but see below for *which* guess |
| destination | unchanged | the manual |

The cycle count is the weakest of these. Nothing in the repo can currently confirm
it, and a real 68000 spends some data-independent time deciding the divisor is zero.

**The real uncertainty is 10 vs 12, not 10 vs 6, and that is worth stating precisely
because "extrapolated" otherwise reads as "arbitrary".** Of the 7-access short-frame
cases (`ssp -= 6`), `CHK` contributes **204 at idle 10** and **101 at idle 12** —
exactly 38 and 40 cycles — while the twelve groups with no operand comparison to make
(`ANDItoSR`, `EORItoSR`, `ILLEGAL_LINEA/F`, `MOVEfromUSP`, `MOVEtoSR`, `MOVEtoUSP`,
`ORItoSR`, `RESET`, `RTE`, `STOP`, `TRAP`) sit at idle 6, over 18,776 cases. So the
short-frame family is *not* uniform at 6, and 38 is a total the suite really produces
on the trap whose rule divide-by-zero borrows.

What remains unknown is which arm of `chk_idle`'s predicate a zero divisor lands on:
that predicate is about the operands (whether `dval - bound` overflows `i16`), and
nothing says a zero divisor resolves it either way. **Do not "simplify" this to 6 for
family consistency** — 6 belongs to the no-comparison groups, and a divide is not one
of them. `muldiv.rs`'s comment at the `divisor == 0` arm carries the same reasoning.

Implementation note: **guard the zero divisor before calling either timing
formula.** `divs_idle` divides by `|divisor|` and would panic in debug, and a host
panic on guest data violates the rule that a guest fault is an emulated
exception.

## Privilege: `MOVE from SR` is not privileged on the 68000

The 68010 made `MOVE from SR` privileged and most references describe that later
behaviour. On the 68000 it executes normally in user mode:

```
MOVEfromSR   user-mode cases 747   trapped 0
MOVEtoSR     user-mode cases 1290  trapped 1290    <- control
MOVEtoCCR    user-mode cases 756   trapped 0       <- control
```

The `MOVE to SR` control is what makes the zero meaningful rather than a broken
probe. It transfers the full 16-bit SR, not just the CCR (404/404 versus 16/404,
388 discriminating cases).

Privileged in user mode, each trapping on every user-mode case in its group:
`MOVE to SR`, `MOVE to USP`, `MOVE from USP`, `RESET`, `STOP`.

## `STOP` and `RESET`

`STOP` loads `SR := immediate & 0xA71F` and **leaves the PC unchanged** —
`final_pc - initial_pc == 0` across 1,230/1,230 supervisor cases — because a stopped
CPU performs no prefetch refill (zero program-space accesses, 1230/1230). The
habitual `pc += 2` scores 0/1230 here.

`RESET` asserts the reset line for **128 idle cycles** (132 total, 1233/1233), leaves
SR unchanged, and advances the PC by 2. Under the timing law `132 = 4 × 1 + 128`: one
bus access (the queue advance) plus 128 idle cycles.

## `LINK` and `UNLK`

`LINK` pushes `An`'s **initial** value high word first, sets `An := SP - 4`, then
`SP := (SP - 4) + d16`. All three are exact across 2,500 cases.

`UNLK` needs **one** code path, provided the two assignments are ordered
correctly:

```
SP := An + 4        (move the stack pointer first)
An := popped long   (then load, so an An == 7 load lands last and wins)
```

- `An != 7`: `An := popped long` and `SP := An_initial + 4` (1075/1075 each)
- `An == 7`: `SP := popped` (310/310) — the pop's own `+4` is overwritten by the
  load into A7, which the ordering above produces for free

An earlier draft of this file called for two paths. That is wrong, and wrong in the
direction that costs debugging time: with the assignments in the other order
(`SP := An`, load, `SP += 4`) the A7 case yields `popped + 4` and the group scores
1385/2500 — a partial pass that looks like a missing special case and invites one.
Adding the special case then re-breaks it. The ordering is the whole fix.

## `MOVEM`

Five rules, none of which the cycle count can check — the cost depends only on
`popcount(mask)`, which is invariant under every mistake below.

**1. `-(An)` uses a reversed mask, not a reversed loop.** Bit 0 names A7, bit 1 A6,
… bit 15 D0; for every other mode bit *b* names register *b*. Walk the bits
ascending in both cases and `-(An)`'s A7-first descending order falls out.

```
-(An), bit i selects register i          (forward)      0/159   0/157
-(An), bit i selects register 15 - i     (REVERSED)   159/159 157/157
control: (An) mode, forward mask                      154/154
```

The control line is what makes this a measurement: code that always answered
"reversed" would score 0 on `(An)`.

**2. The predecrement register stores its INITIAL value.** 158/158 for the entry
value, 0 for the decremented one. So compute the whole descending sequence from the
entry `An` and update `An` exactly once at the end. Decrementing per register
stores the wrong value in precisely the case real code uses —
`MOVEM.l D0-D7/A0-A7,-(A7)`.

**3. The to-registers direction always performs one extra discarded word read**, at
`base + count * size`, 1,445/1,445 across every mode including PC-relative. It is
the pipeline reading one word past the list. `(An)+` still advances by only
`count * size`, so the extra read does not count toward the increment. Omitting it
leaves every to-registers case one access and 4 cycles short — and `(want - got) %
4 == 0` then points at a missing access rather than a wrong constant.

**4. `MOVEM.w` to registers sign-extends each word to all 32 bits**, data registers
included (698/698). This is the one word-sized write into a `Dn` that does *not*
preserve the upper half.

**5. The PC-relative extension base is `opcode + 4`**, not `opcode + 2`, because
the mask word sits between the opcode and the extension word (24/24, 21/21, 19/19,
19/19; `op+2` and `op+6` both score 0). Reads in these two modes are in **program**
space — visible in the fault status word's `fc` bits, 2/6 against 1/5 for the
data-space modes.

Cycles are linear in the register count:

```
cycles = base(direction, mode) + k * popcount(mask)        k = 4 (.w), 8 (.l)

                    reg->mem      mem->reg
(An)                   8             12
(An)+                  -             12
-(An)                  8              -
(d16,An)              12             16
(d8,An,Xn)            14             18
(xxx).w               12             16
(xxx).l               16             20
(d16,PC)               -             16
(d8,PC,Xn)             -             18
```

⚠️ Two traps in this table. **Absolute short and absolute long must be split** —
grouping mode 7 together produces an apparent CPU irregularity that is purely a
grouping artefact. And **`-(An)` charges no address-formation idle**, unlike every
other instruction with that mode: its base is 8, the same as `(An)`, where
`(d8,An,Xn)` is `4*3 + 2` and does charge it. MOVEM subtracts `count * step` in one
go rather than stepping the register, so there is no per-decrement step to pay for.

### A mid-transfer `MOVEM` address error is structurally impossible

The address steps by 2 or 4, so parity is invariant across the whole transfer.
Either access #0 faults or none does — there is no third case. As a 2×2 table with
both off-diagonals exactly zero:

```
MOVEM.w    odd base -> FAULTS  516     odd base -> clean   0
           even base -> clean  639     even base -> FAULTS 0
MOVEM.l    odd base -> FAULTS  489     odd base -> clean   0
           even base -> clean  624     even base -> FAULTS 0
```

Stated directly over all addressing modes: 0 operand accesses completed before the
abort, in all 1,182 + 1,196 faulting cases.

So check alignment **once** against the computed base, before transferring
anything. **Do not write rollback logic**: it would be unreachable, and both groups
would go green with an arbitrary mid-transfer model because no vector can reach it.
This is unlike `DBcc` expiry or divide-by-zero, which are real-but-unsampled paths
worth extrapolating with unit tests — this one cannot occur on the hardware at all,
so there is nothing to extrapolate to.

`MOVEM` is nonetheless the **only write-fault site outside `MOVE`** (595 `.w` + 585
`.l`). The stacked PC is `opcode + 6 + 2 * ext_words` in every bucket and both
directions, and the IR is the opcode. The `-(An)` fault address is `An - 2` at both
sizes — the low word of the first descending long — while every other mode faults
at the base.

## `MOVE to CCR` / `MOVE to SR`: the rewind-and-refill tail

These two share one schedule, and it is not the ordinary single-`<ea>` one. After
reading the operand the CPU **rewinds the PC by 2 and refills both queue slots**:

```
mode 0        i4 P-2 P+0                12   dpc +2
(An),(An)+    R i4 P-2 P+0              16   dpc +2
-(An)         i2 R i4 P-2 P+0           18   dpc +2
(d16,An)      P+0 R i4 P+0 P+2          20   dpc +4
(d8,An,Xn)    i2 P+0 R i4 P+0 P+2       22   dpc +4
(xxx).w       P+0 R i4 P+0 P+2          20   dpc +4
(xxx).l       P+0 P+2 R i4 P+2 P+4      24   dpc +6
(d16,PC)      P+0 p i4 P+0 P+2          20   dpc +4   (program-space read)
(d8,PC,Xn)    i2 P+0 p i4 P+0 P+2       22   dpc +4
#imm          P+0 i4 P+0 P+2            16   dpc +4
```

The two trailing fetches are a **refill**, not two queue advances: for a register
operand the first lands at `pc - 2`, *before* the instruction's own end, which no
forward-only schedule can produce. The 4 idle cycles are the pipeline restart.
`ANDItoSR` and its two siblings use the same tail.

Mode 0 is the case that pins the access count down — `i4 P-2 P+0` is two accesses
and 12 cycles, so there is no separate queue-advance term to add on top.

## `MOVEP`

`MOVEP` exists to talk to an 8-bit peripheral wired to one half of the 16-bit data
bus. Only `d16(An)` addressing exists. Bytes transfer **most significant first** at
`base`, `base+2`, `base+4`, `base+6` — stride 2, so every access in one instruction
uses the **same** strobe and the pattern is `UU`/`LL` or `UUUU`/`LLLL`, never mixed.

Cycle counts are fixed: `MOVEP.w` = 16, `MOVEP.l` = 24, with **zero idle cycles**.
CCR is untouched.

Reading into a register **merges**: `MOVEP.w` writes only the low word and leaves the
upper half of `Dn` alone (1257/1257 versus 0/1257 for clobbering the register). The
`.l` form cannot discriminate, since four bytes cover the whole register.

## Known-bad suite groups: there are none

`TAS` and `TRAPV` are documented upstream as not verified — TAS's 5-cycle
read-modify-write timing said to be unmodelled by the generator, and TRAPV said to
behave oddly with respect to the S bit. **Both labels were tested directly and
neither reproduces.** All 127 groups now pass 2,500/2,500 — the whole suite is
317,500/317,500, so this section is a record of two retracted labels rather than
of an outstanding problem, and the runner has no `assert_known_bad` any more.

### `TRAPV`

**The label does not reproduce; implement it as an ordinary instruction.** The group
has no address-error cases, so its 2,500 cases are the whole of it, and every rule is
exact:

```
timing law                              2500/2500   two shapes, split cleanly by V
V=0: pc += 2, SR unchanged, 4 cycles    1250/1250
V=1: 34 cycles                          1250/1250
  SR == (initial | S) & !T                  1250/1250   <- the "odd S bit" claim
  vector-7 pair at 0x1C/0x1E, PC == vector+4 1250/1250
  stacked SR == initial SR, SSP -= 6        1250/1250
from USER 623 / from SUPERVISOR 627: frame on the supervisor stack at
  SSP-2/-6/-4, USP untouched — full count from both origins
```

The user/supervisor split is the decisive test, since that is precisely where an odd
S bit would show. Anything listing `TRAPV` as an expected failure needs updating
together with the implementation: a `#[should_panic]` test on a working group fails
*because it does not panic*.

### `TAS` advances the prefetch queue last

`TAS`'s group *did* fail — 392/2500, the 392 being exactly the `Dn` form — and the
cause was one line of scheduling in our core, not a defect in the vectors. Every
one of the 2,108 memory-form failures has **exactly two diffs, both of kind `access`,
and nothing else**: the pipeline-advance program read and the operand write, swapped.

```
ordered access sequence, queue advance AFTER the write   2500/2500
ordered access sequence, queue advance between R and W    392/2500
2,108 discriminating cases, all to "advance last"
```

So `TAS` is the one read-modify-write in the suite that advances the queue **after**
its write; every other one advances between the read and the write. Nothing else
about the group is anomalous — no register, SR, PC, prefetch, RAM or cycle-count diff
appears anywhere in it. The idle is an ordinary EA cost (`Dn` 0, `(An)`/`(An)+`/
`d16(An)`/`abs.W`/`abs.L` 2, `-(An)`/`(d8,An,Xn)` 4), and the value rules are exact
over all 2,108 memory forms: the written byte is `original | 0x80`, **N and Z come
from the ORIGINAL byte** (from the written byte: 1030/2108, with 1,078 cases
discriminating — that is the whole difference between `TAS` and an `OR #$80`), V and C
are cleared, and X is preserved.

What made the label look plausible is that the vectors never use the format's
dedicated `Tas` transaction kind at all — `Tas` **zero**, against 5,540 `Read`, 2,904
`Idle` and 2,108 `Write` — which reads like a generator that gave up on the
indivisible cycle. It is not. The generator records one ordinary read and one ordinary
write, in an order the hardware really uses.

The fix is `Plan::fetch_last` in `ops/alu.rs`, whose sole user is `TAS`'s memory
form. With it the group is 2,500/2,500.

## Exceptions and returns

### The three stacked PCs are three different values

Group-2 exceptions stack the address *after* the instruction; the address-error
frame stacks the faulting instruction's own address. Measured, per group:

```
TRAP  #n   stacked PC == opcode_addr + 2   2500/2500   no queue advance first
TRAPV      stacked PC == opcode_addr + 2   1250/1250   (V=1 cases)
RTE (priv) stacked PC == opcode_addr       1286/1286   no bump at all
```

`RTE`'s privilege violation is the odd one out: it stacks the address of the `RTE`
itself, unbumped, so a re-executed handler retries the instruction rather than
skipping it. Writing `+ 2` there costs 1,286 cases and nothing else.

`TRAPV` performs a **leading program read before testing V**, in both the V=0 and
V=1 cases. The attractive explanation — that it is the exception's vector fetch —
is refuted by the V=0 cases, which take no exception and still perform it. It is an
unconditional queue advance, so the implementation consumes the opcode before
looking at the flag.

### `RTE`'s ordering is forced

Pop, then install SR via the same masking path as `MOVE to SR`, then install PC,
then refill the queue. Installing SR before the PC matters because the refill's
function code depends on S, and refilling before either leaves the queue read from
the old PC. Confirmed six independent ways in the group's 600 clean returns.

`RTE` is the only group whose cases split three ways, each a single access shape at
a single cycle count: 600 clean returns at 20 cycles, 1,286 privilege violations at
34, and 614 address errors at 70 where the popped PC is odd.

### An odd *frame base* is a double bus fault, not vector 3

Every stack frame offset on this core is even, so an odd frame base means the frame
write itself faults while the CPU is already in exception processing. That is a
double bus fault: the 68000 halts, with no frame written and no vector taken. It is
implemented once, in `exception::double_bus_fault`, called first by both
`exception::take` and `exception::address_error` before either of *those two
functions* commits anything — rather than at each of the five handlers that detect
the condition.

That guarantee covers `take`/`address_error`, **not the whole entry boundary**. Two
callers commit state before calling in, and correctly so: `check_interrupts` and
`take_trace` clear `stopped` and refill the prefetch queue on the `STOP`-resume path,
because real hardware reloads the queue when `STOP` is released, before the interrupt
is acknowledged. A resumed entry that then halts has therefore already advanced the
PC by 4 and logged 2 bus accesses. Measured at both sites: `halted=true acc=2
stopped true→false pc 0x1004→0x1008`. Those 2 accesses are charged through
`entry_cycles`'s lead term. The invariant that actually holds across the whole
boundary is narrower and is the one worth stating: **a halting entry writes no frame
word and fetches no vector** — the `acc=2` is the resume refill alone.

**The frame base is not always the active stack pointer, and this is the whole
subtlety.** Exception entry sets S *before* pushing, so the frame always lands on the
**supervisor** stack: `frame_base` is `a[7]` in supervisor mode but `ssp` in user
mode. A misaligned push through an odd **USP** therefore does *not* halt — the frame
goes to the SSP, which may well be even, and that fault writes an ordinary vector-3
frame. Measured: 43,483/43,483 user-mode exception cases put the frame on the
supervisor stack, with the USP form as a control at 0/43,483.

The tempting universal form — "an odd SP halts" — is **false**, and its parity
argument holds only where the faulting stack and the frame stack are the same
pointer, i.e. every supervisor-mode case. Reading the *active* SP instead scores
~50%: the coin-flip signature of a predicate that is itself half true.

**The suite does not sample the halt at all.** `LINK`, `PEA`, `MOVEM`, `RTE` and the
trap handlers have zero odd-A7 cases — the generator always starts A7 even — so both
the halt and the alternative go green either way. Two Task 10 unit tests asserted the
vector-3 outcome; that expectation is retracted, the alignment checks that produced it
are not.

⚠️ **Do not "simplify" `frame_base` to `cpu.a[7]`.** That mutation passes every unit
test and all 317,500 vector cases, because the function is consumed only through
`& 1` and is therefore observable only where `a[7]` and `ssp` differ in *parity* in
user mode. One test exists for exactly that case
(`in_user_mode_the_frame_base_is_the_ssp_not_the_active_sp`) and it is the only thing
on the branch that catches it.

### A halted entry is charged for the accesses it made, not for the frame it skipped

The timing law is what settles this, and the halt paths were violating it. A double
bus fault returns before the frame writes and the vector fetch, so a constant that
pays for them contradicts the core's own bus log:

```
                        cycles returned   accesses logged   the law wants
RTE / odd SSP                 58                0                 0 + idle
PEA / odd SP                  58                1                 4 + idle
trace entry / odd SSP         34                0                 0 + idle
trace via STOP resume         34                2                 8 + idle
IRQ entry / odd SSP           44                2                 8 + idle
```

Every discrepancy was divisible by 4, which is the law's diagnostic for a missing
*access* rather than a wrong constant. `exception::entry_cycles` now returns
`4 × accesses actually made + HALTED_IDLE_CYCLES` on the halt path, so the access
term is derived from the log rather than memorised.

The access counts above are derived. **The idle term is not measurable at all** —
0 of 317,500 cases halt (A7 is even in every initial state; the control for that zero
is the *stacked* fault address, odd in 55,606/55,606, so odd addresses are visible to
the query and the zero is a fact about A7). `HALTED_IDLE_CYCLES = 4` is therefore
chosen, not derived, for two statable reasons: it equals what every *subsequent*
halted step costs, and it is non-zero, so a cycle-budgeted driver loop still advances
its clock. Both properties are asserted; the literal 4 is not.

⚠️ Note the trace and IRQ rows are the only halt paths with a **non-zero** access
count, because clearing `stopped` refills the queue *before* the entry. A halted cost
is therefore not a constant, and a test asserting only `HALTED_IDLE_CYCLES` cannot
reach those two paths.

### The interrupt-acknowledge cycle is spent as idle, because `Bus` cannot represent it

The manual decomposes interrupt entry as 44 = `4 × 8 + 12`: eight bus accesses, one
of them the IACK. This core emits **seven** — measured, `cycles=44 accesses=7 (r=4
w=3)` — and reaches the same 44 as `4 × 7 + 16`.

Both decompositions are correct arithmetic and only one of them describes this core.
`Bus` carries no function code, so an IACK is not distinguishable from an ordinary
read; emitting one would add a transaction the suite's measured access shape does not
contain. The 4 cycles are therefore spent as idle and *named* as such —
`exception::IACK_AS_IDLE_CYCLES` — rather than hidden inside a bare `16`. Do not
"fix" this by synthesising the eighth access: it breaks the group's shape.

Recorded so that a green 127/127 is not misread as full coverage. Each of these is

⚠️ **`TxKind::Tas`: the dead arm is documented, not deleted.** The full transaction
census, over all 127 files:

```
317,500 cases, 1,783,580 transactions
   Idle          333,171      Read           832,245      Write          562,558
   ReadAddrErr    53,160      WriteAddrErr     2,446      Tas                  0
```

The 1,783,580 denominator *is* the control: every other variant is present in
quantity by the same query, so the zero is a property of the corpus. `binfmt.rs`'s
`3 => TxKind::Tas` decode arm and `runner.rs`'s `Read | Write | Tas` filter are
therefore both unreachable on current data, and each now says so at the site. They
stay: the raw discriminant `3` is part of the on-disk format, so dropping the arm
would turn a valid-per-format file into `BadKind` — a worse failure than a dead
branch — and TAS's read-modify-write has a real bus signature a future suite
version could start emitting. A dead arm that is *known and documented* is fine; a
dead arm that looks exercised is the hazard.

⚠️ **The trace row was recorded backwards once, and the correction matters.** The
original claim was "T is clear in every initial state, so a core that took the trace
immediately would still pass every group." Both halves are false. Measured: **158,894
of 317,500 initial states have T set** (50.0%), spread across **all 127** groups. A
core that traced *before* the instruction boundary instead of after would fail roughly
38% of the suite, not pass it. What is uncovered is the **handler**, because a
one-instruction case never reaches the next boundary — so the deferral is what the
suite checks and the vector-9 frame is what it cannot.

⚠️ **`TAS`: do not restate this row as a sampling gap.** The zero is structural, not a
generator artifact: a byte access has no alignment constraint on the 68000. A prior
version blamed sampling and cited "no odd addresses in the group", which is
unmeasurable as stated — see the format note below. The neighbouring `odd stack
pointer` row *is* a genuine sampling gap and is correct as written.

⚠️ **The T sampling *point* is also uncovered, and is a different fact from the
boundary.** T is sampled at instruction *start*, so a trace is owed on the entry SR
even if the instruction goes on to clear T. That comes from the manual and cannot be
measured here, because no case takes a trace at all. The suite census of instructions
that can clear T — `ANDItoSR`, `EORItoSR`, `STOP`, `MOVEtoSR`, `RTE`; 1,277 clean
cases ending with T clear, `ORItoSR` at 0/591 as the control since `OR` cannot clear a
bit — identifies **where the start-sampling and end-sampling rules disagree** and
nothing more. It was once cited as evidence for reading the final T, which is a census
of instructions being asked a question about sampling points.

What rules end-sampling out is behavioural, not a count: the trace handler ends in an
`RTE` whose popped SR restores T, so an end-sampling core owes a trace for the `RTE`
itself and re-enters the handler having executed nothing. Measured on this core: 1
traced instruction in 200 steps that way, against 4 in 12 with start-sampling
(`single_stepping_with_an_rte_handler_advances_one_instruction_per_trace`).

### Stack-alignment faults are unit-tested only, and guest code does reach the state

Initial `A7` is even in **317,500 of 317,500** cases. The control that makes that a
fact about `A7` rather than about the query: `A0`-`A6` are odd **1,111,722** / even
**1,110,778** over the same scan, so the generator uses odd addresses freely and
deliberately never starts with an odd `A7`.

But **16** groups *end* with an odd active `A7`, across **2,733** cases, so real
guest code reaches the state the suite never starts in:

```
ADD.l 6 · ADD.w 7 · ADDA.l 113 · ADDA.w 114 · EXG 130 · LEA 165 · LINK 1293
MOVEA.l 109 · MOVEA.w 104 · MOVEM.l 171 · MOVEM.w 157
SUB.l 9 · SUB.w 13 · SUBA.l 92 · SUBA.w 100 · UNLINK 150     = 2,733 over 16 groups
```

`LINK`'s 1,293 is 47% of the total on its own, which is the expected shape: `LINK
#-odd` is the one instruction whose *documented* purpose is to move `A7` by a
caller-chosen amount. The second fault from that state is a **halt**, not recursion.

⚠️ **Three plausible predicates give three different answers here, and that is how
the wrong one got written.** Re-derived independently for this section:

| predicate | answer |
|---|---|
| **active SP, selected by `final_.sr`'s S bit** | **2,733 over 16 groups** |
| either `final_.ssp` or `final_.usp` odd | 3,284 over 17 |
| `ssp` odd alone | 1,379 over 16 |
| `usp` odd alone | 1,905 over 17 |

The active-SP form is the right one, because the claim is about the `A7` the *next*
instruction would push through. The union predicate's extra group is exactly one —
**`MOVEtoUSP`, 551 cases** — where the case writes an odd value to `usp` while
running in supervisor mode, so the odd register is not the active stack pointer at
the end of the case. That single group is the entire difference between "17 groups"
and "16", and it is a real instruction doing a legal thing, not noise. An earlier
revision of this file's coverage list carried 3,284/17.

### `check_interrupts` rests on four assertions, not on 317,500 cases

**This is the single most important caveat in this file.** A reader deciding where to
trust this core needs to know which parts rest on the suite and which do not.

Nothing in the suite exercises interrupt entry: 317,500 cases scanned, **0** read an
autovector (`0x60`-`0x7F`), and vectors **25-31 are fetched 0 times**. The control
for those zeros is the same query finding vector 3 in 55,606 cases and vector 6 in
1,326, so it can see a vector fetch where one exists. `check_interrupts` is covered
by hand-written unit tests alone, and its **44**-cycle figure is **extrapolated, not
measured** — see the IACK section above for why 44 decomposes as `4 × 7 + 16` here
and `4 × 8 + 12` in the manual.

### The interrupt line is level-triggered and the caller owns deassertion

`pending_irq` is a *level*, not an edge. `set_irq` records it and it stays recorded
until the caller lowers it — the CPU never clears it, because hardware does not.

Levels 1-6 are self-limiting even when held: entry raises the SR mask to the serviced
level, so the same level cannot re-enter until the handler's `RTE` restores the old
mask. **Level 7 has no such protection.** It is non-maskable, so no mask value can
block it, and a held level 7 re-enters its own handler at every boundary: the PC stays
pinned at the handler's first instruction while the stack walks down 6 bytes per pair.
Measured: `a[7]` 0x3000 → 0x2FC4 in 10 steps.

This is left level-triggered deliberately. Edge sensitivity would change the interrupt
contract that `crates/testrunner/tests/integration_asm.rs` relies on — its
`interrupt_mid_loop_resumes` program calls `set_irq(0)` once the handler has run,
which is a driver deasserting a line and is the correct shape.

### `Transaction.addr` is word-aligned by construction — do not measure alignment with it

The suite's bus is 16 bits wide, so `Transaction.addr` is the **word** address the CPU
drives; a byte access appears as an even address plus a UDS/LDS strobe. Measured: **0
odd of 1,394,803** non-fault accesses — and, as the control that makes the point, **0
odd of 55,606 transactions belonging to address-error cases**, where an odd address is
present by definition. The odd byte address survives only in the *stacked* fault
address, and it survives there **universally**: `t.addr == (stacked & 0xFF_FFFF) - 1`
in **55,606 of 55,606** cases, against `t.addr == stacked & 0xFF_FFFF` in **0**. This
is a law, not a correlation. (An earlier revision of this section put the first figure
at 54,652 — a stale number that reproduces under no predicate; `exception.rs:79` and
`:104` already cite 55,606/55,606.)

So any claim of the form "the suite never uses an odd address", measured over
`t.addr`, is **vacuous** — the projection destroys the property before the query runs.
Read the stacked frame instead.

**Mask the stacked value to 24 bits before comparing.** `t.addr` is not just
word-aligned by construction; it is also **24-bit** by construction, because the
68000 drives 24 address lines. The suite leaves junk in stacked bits 24-31 —
nonzero in **49,649** of the 55,606 cases — so the unmasked comparison
`t.addr == stacked - 1` holds in only **5,957**. That is the same vacuity one level
up: an *equality* between a 24-bit bus address and a 32-bit stacked word is
meaningless until the widths match, exactly as an *alignment* claim over `t.addr`
is meaningless because the low bit was never there.

**The general rule, since this file now records three instances of it: a predicate
consumed only through a projection can be tested only through that projection.**
`t.addr` is word-aligned *and* 24-bit by construction, so neither an alignment claim
nor an equality-with-a-32-bit-word claim can be scored over it — the property is gone
before the query runs, and the query answers cheerfully. The three instances are the
alignment vacuity above, the width vacuity below it, and the `TAS` coverage row's
earlier "no odd addresses in the group" phrasing, which was unmeasurable as stated.
Before scoring a rule, ask what the projection you are reading has already destroyed.

### Identify an address error by its aborted access — three predicates, three answers

Counting address-error cases looks trivial and has three plausible spellings. Measured
on the same corpus, they give **55,608**, **55,607** and **55,606**:

| predicate | count | why it is wrong |
|---|---|---|
| any read at `4v` | 55,608 | admits ordinary data reads at low addresses — vector 3 plus a spurious vec 17 and vec 22 |
| a read at `4v` immediately followed by one at `4v+2` | 55,607 | still admits one case |
| **an aborted access (`ReadAddrErr` \| `WriteAddrErr`)** | **55,606** | correct: no data access can imitate an aborted one |

The single case separating the last two is `ADD.l D6,(xxx).w`, whose absolute operand
address is `0x0C` — so it reads `0x0C` and `0x0E` as **data**, in the correct order,
and a vector-shaped query cannot tell that from vector 3's fetch. Tightening the
address pattern does not fix this, because the pattern is not the discriminator: the
*kind* is. The aborted access is a distinct transaction kind that nothing else
produces, which makes it the only sound predicate, and 55,606 in 55,606 cases across
63 groups is what it yields.

Two conclusions worth carrying forward. First, the near-agreement is the danger: a
predicate that is wrong by one case out of 55,607 will survive any amount of
eyeballing, and only a second predicate disagreeing exposes it. Second, this is the
same discriminator the branch-displacement section needs to exclude faulting cases,
where the rival predicate ("SR gained S") is wrong by 1,006 — a fault is identified by
what it aborted, not by what it changed.

## Integration diagnostics — instruction-sequence evidence

`crates/testrunner/tests/integration_asm.rs` contains five hand-assembled programs
that test instruction *sequences*, which the per-opcode vector suite structurally
cannot test. The Tiny68k diagnostic path was not taken: the project constraint
forbids fetching any binary from the internet, and no assembler is installed on
this machine (verified: `vasm`, `vasmm68k_mot`, `m68k-elf-as`, `m68k-linux-gnu-as`
all absent).

Each program boots at `0x1000` with SSP `0x8000`, runs to `STOP`, and asserts on
final state. All five pass on the current tree.

### Confirmed by the integration suite (extrapolated — hand-written programs, not vectors)

**`nested_bsr_returns_correctly`** — 8 steps, STOP reached, `d0=2`, `a7=0x8000`.
Nested BSR/RTS unwinds to the correct depth; stack does not drift.

**`movem_roundtrip_preserves_all_registers`** — 7 steps, STOP reached,
`d0=0x12345678`, `a1=0x4000`, `a7=0x8000`. MOVEM round-trip preserves all
registers through the stack; the reversed-mask rule for `-(An)` is correct.

**`trap_and_rte_resume_correctly`** — STOP reached, `d0=2`, `a7=0x8000`.
TRAP #0 enters vector 32 (address `0x80`), stacks `opcode_addr + 2`, handler

**`interrupt_mid_loop_resumes`** — 202-ish steps, STOP reached, `d1=1`,

popped. The handler raises the mask to 4 on entry, preventing re-entry while

**`dbcc_loop_iterates_exactly`** — 23 steps, STOP reached, `d0=10`,

**not** present.

### Encoding notes

Three opcode words in the five programs are absent from the 317,500-case vector
suite (`0x7000` MOVEQ #0,D0; `0x203C` MOVE.l #imm,D0; `0x343C` MOVE.w #imm,D2).
All three are sampling gaps in the generator — the instruction family and
addressing form are present for other register numbers. Do not replace them with
sampled siblings: testing D0 where the suite tests D2 is intentional coverage
the suite lacks.

Branch displacements: the 68000 bases word-displacement branches on the
*extension word's* address (i.e. `opcode_addr + 2`), and the 8-bit short form
on `opcode_addr + 2` as well (one word, no extension). Both forms use the same
base, which means the two BSR displacements in `nested_bsr` (`+6` and `+4`)
target `0x100A` and `0x1012` — not `0x1008`/`0x1010` as a naive opcode-relative
reading would suggest. The `dbra` in `dbcc_loop` targets `0x1006` (loop body),
and `bne.s` in `interrupt_mid_loop` targets `0x1004` (loop target). All confirmed
correct by execution.

## How to check that a claim in this file is still checked

Two procedures, recorded because the results in this file are only as good as the
tests that hold them in place, and a green suite says nothing about whether a
particular constant is *pinned*.

### Manual mutation testing

No mutation-testing dependency is in this workspace, and none should be added for
this: the interesting mutants are a handful of specific constants, and choosing them
by hand is the point. The procedure:

1. Change one constant or one operator, by hand.
2. Run `cargo test --workspace --release` and record **which** tests died, not just
   how many.
3. Revert, and confirm with `git status --porcelain` **before the next mutant**.

Step 3 is not bookkeeping. Running a second mutant on top of an incompletely reverted
first produces a result that describes neither, and the failure is invisible — both
mutants "die", so the transcript looks like success. Verify the clean tree between
every pair.

What the results mean: a mutant that kills **many** tests across several modules is
evidence those sites express *one* claim, and consolidating them is safe. A mutant
that kills **nothing** means the constant is a comment, not a check — either write the
test that pins it, or label it extrapolated in this file. **Every rule labelled
extrapolated above should be asked the question "what mutant would catch this?", and
several of them answer "none".** That is a legitimate answer for a value the corpus
cannot reach; it is not a legitimate answer for one it can.

The sharpest instance on this branch: four spellings of the short-frame entry cost
were consolidated into `exception::SHORT_FRAME_ENTRY_CYCLES`, and mutating it kills
**7** tests across all four former sites while leaving `TRAPV`'s untouched — which is
simultaneously the evidence that the four were one claim and that `TRAPV`'s
identical-looking `34` is a different one (`4 × 8 + 2`, not `4 × 7 + 6`).

### A rule a downstream mask makes untestable

`MOVE <ea>,CCR` writes bits **4..0**. It was written as a *byte* mask,
`(sr & 0xFF00) | (val & 0x00FF)` — the weaker claim — and behaved correctly anyway,
because `set_sr` masks with `SR_MASK = 0xA71F` and clears bits 7-5 a second time. The
weaker rule is *recovered* downstream, not correct.

The instructive part is what happened when a discriminating test was attempted. The
obvious move is to drive a full instruction with bits 5-7 set in the source and assert
`cpu.sr`. **That test passes under both masks**, and no choice of operand fixes it: the
difference is destroyed by `SR_MASK` after the code under test has run. The suite cannot
help either — 0 of 317,500 initial SRs have bits 5-7 set.

So the fix was to give the rule a name, `system::move_to_ccr_value`, and assert its
return value. Mutating it back to the byte form now fails that test and nothing else,
which is the confirmation that it is checked. Before extraction, the byte form passed
**all 206 unit tests and 127/127 groups**.

The general shape, and it is the same one as `Plan::writes` below: **when a value passes
through a normalising step before it becomes observable, no test of the observable can
check the step before it.** Extracting the rule into something that returns a value is
not refactoring for tidiness — it is the only thing that makes the claim checkable.
Assert the artifact, not the state some later mask has already corrected.

### A dead field, and why the obvious invariant was the wrong one

`alu::Plan::writes` had **13** builder call sites and **0** reads of the field. Four
reviewers independently proposed the same fix: rather than delete it, assert it, so the
recorded intent becomes a live invariant. That is the right instinct — `Plan` carries
both live flags (`fetch_last`, read twice) and inert ones with identical shape, so a
reader cannot tell them apart without grepping, which an assertion fixes and a deletion
does not.

But the invariant that was proposed — `plan.writes == (compute returned Some)` — is
**false**, and measuring it is the whole lesson. Instrumented over the full suite:

```
writes == result.is_some()                        fails 82,380 times
writes == (result.is_some() && dst is memory)      fails  7,918 times   <- opposite direction
writes set while nothing is written                       0 times
```

The first fails wherever the destination is a register (`writes` false, a write
happens); the second fails on `BSET`/`BCLR`/`BCHG` into a register, which set `writes`
legitimately. Two plausible equalities, both wrong, failing in opposite directions —
so the sound statement is the **implication**, `!writes || result.is_some()`, and that
is what ships as a `debug_assert!`.

Had either equality been asserted on the strength of it reading correctly, the result
would have been a false claim shaped exactly like a check. **An invariant is a
measurement too.** The assertion's own control: making `shift::memory_form` return
`None` fires it, naming the field — an assertion never observed to fail has not been
shown to be able to.

A worked example of the *other* outcome, where mutation settles a disputed figure.
Two sites described `ADDX`/`SUBX`'s same-register memory-pair count, one saying 514
and one saying 526, and the branch ledger recorded them as one stale number needing
alignment. Measuring showed something different: **639** same-register non-faulting
cases in total, of which **526 exclude `A7`** — and the site saying 526 states exactly
that narrower scope, so it was right all along. The 514 reproduces under no predicate.
The mutant (roll the source's predecrement back so both operands read one address)
fails exactly 639 cases across all six groups, confirming the census independently.

**Two counts that disagree are not automatically one error.** Reconciling them to a
single value would have replaced one right answer with a wrong one; the fix is to
state the scope beside every count, which is why this file does that throughout.

⚠️ **A total matching is not a decomposition matching.** `34` is reached as `4 × 7 +
6` by 18,776 cases and as `4 × 8 + 2` by `TRAPV`'s 1,250. Any test asserting only the
total cannot tell those apart, and a great many of this core's cycle tests assert only
the total.

### Zero-lead forms cannot discriminate a lead term

Related, and the mechanism by which a real defect survived thirteen tasks of a fully
green suite. If a handler's cost is `4 × lead + idle + tail` and the probe you choose
has `lead == 0`, the test scores identically whether the lead is charged or dropped.
`PEA (A0)` and `MOVE.w (A0),D0` both have `lead == 0`; a `pea` fault path that omitted
its lead idle entirely passed a test that looked like coverage.

So when testing a term, **choose a form in which that term is non-zero**, and prefer
parameterising over several forms — `PEA (0,A0,D0.w)`, `(d16,An)`, `-(An)` — so that a
single row with an accidentally-zero term cannot carry the whole assertion. Where a
fault path is involved, assert the **bus log is empty** alongside the cycle count: a
handler claiming a framed cost for a frame it never writes is the exact defect five
sites on this branch had, and only the log exposes it.

### A `0/N` that chance predicts is not a measurement

The zero-value blind spot is not confined to cycle terms. The disassembler's
`format_disp_an` special-cased `disp == 0` to `(An)`, so `1028 0000` (4 bytes) printed
`move.b (a0),d0`, character-identical to `1010` (2 bytes). Under MOVEP — which shares
the helper and whose **only** `<ea>` is `(d16,An)` — `0108 0000` printed
`movep.w (a0),d0`, naming an addressing mode the instruction has no encoding for. The
bug is now fixed and pinned by two tests; what belongs in this file is how the
measurement around it nearly went wrong.

First query: *does the suite exercise a zero MOVEP displacement?* Answer **0 of 5,000**
MOVEP cases. Written down bare, that reads as "the generator excludes it", which would
have justified leaving the path unasserted. It supports no such conclusion. The
corpus-wide rate of a zero second prefetch word is **5 of 317,500**; at that base rate
the expected count in 5,000 cases is **0.08**, so observing zero is exactly what chance
predicts. The `0/5,000` measures the base rate, not MOVEP.

The rule this makes concrete, and it is stronger than "run a control that must produce
output":

> Before reading a `0/N` as a property of the thing you selected on, compute what `N`
> times the **background** rate would have produced. If the answer is under 1, your
> zero is consistent with the property being present and is evidence of nothing.

The control that did carry weight was constructive rather than statistical:
hand-assemble the word and look at the output. `0108 0000` → `movep.w (a0),d0` is a
one-line proof, and no amount of suite querying could have produced it, because the
suite carries no text. Where a claim is about **rendering**, the vectors cannot be the
control — see the module docs' note that only the signed spelling is a correctness
claim and the rest is house convention.

Two further notes for whoever touches this next. `len` was correct throughout (4 and
2), which is why the defect was originally filed Minor: a debugger stepping by `len`
stayed in sync, and only a human reading the listing was misled. And the fix belongs in
the shared helper, not in a `decode_movep` special case — the same argument as
`format_index_reg` below: the general helper was the thing that was wrong, and MOVEP
merely made it visible.

### Near-duplicate blocks let a fix be written and still leave the bug

`format_index_ea` and `format_index_pc_ea` render the two indexed addressing modes.
They shared **8 of 11 lines verbatim** and differed in exactly one substantive way: the
PC form wrote `ext as i8 as i32`, the `An` form `ext as i8` printed with `{:X}`. So a
displacement of −16 rendered `-$10` in one mode and `$F0` in the other, and a second
site (`format_disp_an`, on an `i16`) rendered it `$FFF0` — which reads as 65,520
*forward*. The file disagreed with itself three ways about the same rule, while
`link a0,#-16` and `moveq #-1,d0` had the sign right all along.

The methodological point is about what "fixed" means. Correcting the sign at each of
the three sites would have made every current test pass and left the **next** copy free
to diverge again: nothing in the code would say the three renderings are one rule. The
fix was to extract `signed_hex` and `format_index_reg`, so the duplication that allowed
the divergence no longer exists. Stated generally:

> When two blocks are near-identical and disagree, the disagreement is the symptom and
> the duplication is the defect. Extracting the shared lines makes that class of
> divergence **unwritable**; patching each site only makes today's instance absent.

This is also why the sign bug and the duplication were fixed in one commit rather than
two: extracting the helper is what makes the sign bug unwritable, so splitting them
would have left the weaker fix standing on its own in history.

### Consolidating four copies of a rule removes the cross-check that guarded it

The control-addressing predicate — `(An)`, `(d16,An)`, `(d8,An,Xn)`, `(xxx).W`,
`(xxx).L`, `(d16,PC)`, `(d8,PC,Xn)`, and nothing else, 28 of the 64 `(mode, reg)` pairs
— was stated in **four** places: `ea::modes::control`, a private `is_control` in
`ops/branch.rs`, a hand-inlined `matches!` in `opcode_space.rs`'s JMP/JSR arm, and
`jump_idle`'s seven match arms. The first three were verified to agree on **64/64**
pairs (control: a predicate dropping mode 6 disagrees on 8/64, so the comparison
discriminates) and consolidated onto `ea::modes::control`.

The part worth recording is what consolidation *cost*. `modes::control` had **no test**.
Before the merge it did not obviously need one: two independent copies of the rule stood
beside it, so a wrong `control` would have made them disagree and something would have
failed. After the merge every caller asks the same function, a wrong answer is
consistent everywhere, and nothing contradicts it. Deduplication converted an accidental
cross-check into a single point of failure.

So the merge came with `control_modes_are_the_seven_addressable_without_stepping`, a
hand-enumerated truth table over all 64 pairs. Enumerating rather than re-deriving from
`matches!` is what makes it a check: a test written as `assert_eq!(control(m, r),
matches!(m, 2 | 5 | 6) || ...)` restates the implementation and passes any mutation of
it. The set size (28) is asserted separately so that a truth table edited to match a
wrong implementation still fails.

> Before removing a duplicate, ask what would have failed if the surviving copy were
> wrong. If the answer was "the other copy", the duplicate was carrying a test, and
> deleting it without writing that test down is a net loss even though the code got
> shorter.

Mutation check: `control` widened to `reg <= 4` (admitting `#imm`) kills
`disasm_illegal_iff_cpu_illegal`, `implemented_tasks_claim_exactly_the_legal_encodings`
(at `41FC`), `no_opcode_panics`, and the new truth table. It kills **no suite group** —
the corpus contains no illegal encodings, so legality rules are structurally outside
what the vectors can test.

Related: `jump_idle`'s fallthrough returned **0**, a plausible idle count, from an arm
reachable only if `register` installed JMP/JSR outside the control set. It now
`debug_assert!`s and names the offending mode. Confirmed by the mutant: the debug-mode
opcode sweep reports `jump_idle reached a non-control mode 7/4` and points at the
dispatch table, where the release-mode `unreachable!` in `jump_target` reports only that
`ea::resolve` returned a non-`Mem`. **An unreachable arm returning a defensible-looking
number is worse than one that panics** — it converts a dispatch-table error into a cycle
count off by a small multiple of 2, which reads as a timing constant being wrong.

### A mutation score on dead code measures only its deadness

`exception::push16` pushes a word the simple way: SP down 2, write, sync the shadow SP.
Removing the shadow sync kills **no test in the workspace**. Filed as a `0` in an early
draft of the table above, where it would have read as "the shadow SP is unpinned".

It means nothing of the sort. `push16` has **zero callers**. Any mutation of it scores
zero, including replacing its body with `unreachable!()`. The number describes the call
graph, not the stack model.

> Before recording a mutant's score, confirm the mutated code executes. A zero from an
> uncalled function looks identical to a zero from an untested one and licenses the
> opposite conclusion.

The real measurement for the same question is `ops::system::sync_sp`, which *is* called:
making it a no-op kills exactly one test
(`link_a7_pushes_the_entry_stack_pointer`) and no suite group. That is the honest
figure — and one test is the right amount for something `sync_sp`'s own docs call
belt-and-braces.

Why the suite cannot see it: `a[7]` holds the active stack pointer and the matching
`usp`/`ssp` slot goes **stale** — after `BSR` in supervisor mode `a[7]` is `0x2FFC`
while `ssp` still reads `0x3000`. This is sound, because `set_sr` saves the outgoing
`a[7]` into the correct slot before loading the incoming one, so the stale value is
always overwritten before it could be read as active. The invariant is the weaker
*"the inactive pointer is valid in its slot; the active pointer is valid only in
`a[7]`"*, and the harness reads the active SP from `a[7]` too — so no vector case can
observe a stale shadow at all. `M68k::a`'s doc previously said `a[7]` "mirrors"
`usp`/`ssp`, which states the strong invariant the code does not maintain.

While confirming this, `push16`'s comment turned out to promise something the same file
refutes fifty lines later: "used by future instruction handlers (TRAP, bus-error frame,
etc.)". `take` explains that the 68000 writes the short frame in a **non-sequential**
bus order that three sequential pushes cannot produce, so `TRAP` — the named example —
is the clearest case that can never be a caller. A dead helper is cheap; a dead helper
advertising itself as the way to do something impossible is not.

### Five chosen examples let two mutants through; an exhaustive reference caught both

`asl_overflow` is the closed form of "did the sign bit change at any step of the
shift". Its test `asl_overflow_is_a_mid_shift_predicate` carried five direct asserts,
which read like coverage of a nine-line function. Mutating it says otherwise
(measured, Task 14):

| Mutant | Hand-written 5 asserts | Exhaustive reference | ASL suite groups |
|---|---|---|---|
| `count >= bits` → `count > bits` | killed | killed | 3/3 killed |
| `k = count + 1` → `k = count` | killed | killed | 3/3 killed |
| drop the `top == (1<<k)-1` disjunct | **survived** | killed | 3/3 killed |
| mask `(1<<k)-1` → `(1<<k)` | **survived** | killed | 3/3 killed |
| `return v != 0` → `return true` | killed | killed | **1/3 killed** |

Two of five mutants walk past the hand-written asserts, and both are in the same
clause: the all-ones disjunct, which is the branch for a **negative** operand whose
sign never changes. Every one of the five asserts uses a non-negative operand, so that
half of the predicate was never evaluated. The asserts pin the two branches and two
boundaries — the things that were on the author's mind — and miss the `bits - k` shift
amount, the mask constant, and the negative case.

> Chosen examples cover the cases the author thought of, which are the cases they
> already got right. For a small total function, compare it against a slow reference
> over the whole input space instead; the reference must be written the obvious way,
> or it shares the bug.

The new `asl_overflow_matches_a_step_by_step_reference` shifts one bit at a time and
watches the sign, exhaustively at 8 and 16 bits (256×64 and 65,536×10 pairs) plus the
`count + 1 == 32` boundary at long size. Note the mutant it does **not** need to catch
alone: the suite kills every mutant here, so the reference is not covering a gap in
the vectors — it is covering a gap in the *unit* test, which is what localises a
failure to this function instead of to whichever of 2,500 cases happens to trip.

The bottom row is the narrowest suite margin in this audit and worth its own number.
`return true` — dropping the zero-operand exemption from the saturating branch — is
caught by **three cases out of 7,500**. 1,285 of 2,500 `ASL.b` cases reach `count >= 8`
and 3 carry a zero operand; `ASL.w` reaches it 706 times and `ASL.l` 624, with a zero
operand neither time. Applying the `0/N` rule from above before reading anything into
those two zeros: a zero operand appears 0/2,500 times *anywhere* in `ASL.w` and
`ASL.l` at any count, so the expected overlap is 0.00 and the zeros measure nothing.
In `ASL.b` the rate is 6/2,500 and the expected overlap is **3.08 against 3 observed**
— the suite is not targeting this input, it is hitting it at exactly the rate chance
predicts. A slightly differently-seeded corpus would have left this clause unpinned by
vectors entirely.

### A reference implementation cannot check the part it copied

`shift`'s closed forms are validated against `one_step_at_a_time`, a loop that does
what the hardware does. That is the right design, and its docstring says it exists so
the forms are checked "against the definition rather than against a restatement of
themselves". For one branch, it is a restatement of themselves.

The loop cannot express a zero-iteration case's flags, so the `count == 0` early return
is **copied** into the reference verbatim. Mutating it in both copies —
`c: kind == Kind::Rox && x0` → `c: false` — leaves
`closed_forms_match_the_step_by_step_reference` **green** (measured, Task 14).
Mutating one copy kills it, which is precisely the trap: every casual experiment on
this test suggests it covers the zero-count rule, because the natural way to test a
comparison is to break one side.

> An equivalence test measures agreement, not correctness. Where the reference shares
> code with the subject, it certifies the shared part unconditionally. Ask which lines
> the two have in common before crediting the comparison with covering them.

The rule is not unpinned — the both-copies mutant fails the six `ROX` suite groups
(`roxl_b/w/l`, `roxr_b/w/l`) and one unit test, and six is the right number since the
rule is `ROX`-specific. The defect was the docstring's claim, now corrected in place.
The duplication itself is kept: factoring it into a shared helper would make the two
sides agree by construction for *every* mutation and lose the one-copy signal too.

Compare the `asl_overflow` section above, where the reference shares *no* code with
the subject and consequently catches two mutants the subject's own test misses. Same
technique, opposite outcome, and the difference is exactly how much was copied.

### `cargo doc` in the gate cannot see a link to a private or `cfg(test)` item

The verification gate runs `cargo doc -p m68k --no-deps`, which passed clean while the
crate contained **two** unresolved intra-doc links: a pre-existing `[`fetch_word_dyn`]`
in `cpu.rs` and one this task introduced. Both are invisible by default because
rustdoc does not document private items, so it never resolves paths written in their
docs — and `lib.rs`'s `#![deny(rustdoc::private_intra_doc_links)]` does not help, since
that lint fires on links that *resolve* to a private item, not on ones that fail to
resolve at all.

The second case has no linking fix: the target was a test function, and the `tests`
module is `#[cfg(test)]`, so no rustdoc invocation can resolve a path into it. Both are
now plain code spans with a note saying why.

> To check intra-doc links in a crate that is mostly private, the gate's `cargo doc` is
> not enough. Use
> `cargo rustdoc -p m68k -- --document-private-items -A rustdoc::private_intra_doc_links`
> — private items get documented so links resolve, and the `-A` suppresses the
> thousands of expected private-link warnings that would otherwise bury the real ones.
> This is a diagnostic, not a gate step: it is not wired into CI, so an unresolved
> private link can reappear.

### The benchmark is not a check

`cargo bench -p m68k` reports roughly **800 MHz** simulated against CPS-1's 10 MHz —
about an **80×** margin, at a measured mean of **9.33 cycles per instruction**. Treat
that as a liveness signal and nothing more. An 80× margin will not catch a 5× or 20×
regression, so no performance claim in this project rests on it; what its assertion
catches is "the core stopped executing". The non-degeneracy census it prints first (7
distinct PCs, 4 distinct cycle costs `{4, 8, 10, 12}`) is the part that catches "still
executing, but no longer executing *this*" — a one-instruction spin loop reports a
fine MHz figure. The absolute number also moves with host load: three measurements of
the same workload on this branch gave 817.8, 734.0 and 796.1 MHz. The **margin** is
the durable claim; the MHz is not.
